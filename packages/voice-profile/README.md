# voice-profile-core

A portable model of "who I am and how I write", with swappable persistence.

**Zero runtime dependencies.** Nothing here imports from AetherHub, Next.js,
React, Vercel, or a database driver. Deliberately unscoped and product-neutral:
the whole directory lifts out and publishes as-is.

---

## Why it exists

The `social-media-skills` suite reads two files from a project root:
`about-me.md` and `voice.md`. All 17 skills depend on them. That works when
you're sitting in a Claude Code session with the repo checked out, and not at
all on a phone.

This package treats those files as a **projection**, not a storage layer. The
profile lives in a database; `renderMarkdown()` produces the files a skill
expects, and `renderSystemPreamble()` produces the prompt prefix an API route
expects.

---

## Sync direction — read this before touching the files

```
   ┌────────────────────┐
   │   app database     │   ◀── canonical. The only writer. The only truth.
   │   (voice_profile)  │
   └─────────┬──────────┘
             │  syncVoiceFiles()          ONE WAY. NEVER READ BACK.
             ▼
   ┌────────────────────┐
   │  about-me.md       │   ◀── build artifacts. Gitignored. Overwritten.
   │  voice.md          │
   └────────────────────┘
```

**The app database is canonical.** Editing the profile happens in the app, and
nowhere else.

**The markdown files are build artifacts.** They are generated by
`npm run voice:sync`, they are listed in `.gitignore`, and they are overwritten
in full on every sync. Every generated file opens with an HTML comment saying
exactly that, so anyone who opens one to edit it is told on line one not to.

**The flow is one-way and there is no import path.** Nothing in this package
parses `about-me.md` or `voice.md` back into a profile, and nothing should be
added that does. Two writers means merge conflicts, and merge conflicts on a
voice profile mean a silent drift in what your posts sound like. One writer, one
direction, no reconciliation logic to get wrong.

Two consequences worth stating plainly:

- **Hand-edits are lost.** Not "may be lost" — lost, on the next sync, without
  a prompt. The files are output, the way `.next/` is output.
- **Stale files are possible.** The banner stamps the profile's `updatedAt`, so
  a file older than the database is detectable. Re-run the sync; there is
  nothing to merge.

If a skill ever needs to *write* voice data, it should call the app, not the
files.

## Usage

```ts
import {
  createPostgresVoiceStore,
  renderSystemPreamble,
} from 'voice-profile-core';

// Bring your own driver. This adapter never imports one.
const store = createPostgresVoiceStore({
  sql: (text, params) => pool.query(text, params),
});

await store.migrate();                 // idempotent DDL
await store.saveProfile({ aboutMe, voice });

const profile = await store.getProfile();
if (profile) prompt = `${renderSystemPreamble(profile)}\n\n${prompt}`;
```

Writing the files (server-only — this is the one module that touches `node:fs`):

```ts
import { syncVoiceFiles } from 'voice-profile-core/sync';

await syncVoiceFiles(store, { dir: projectRoot });
// → { profileFound: true, written: ['…/about-me.md', '…/voice.md'], updatedAt }
```

Or from the repo root: `npm run voice:sync`.

## Design decisions

**No id parameter, anywhere.** This deployment is single-tenant: one profile,
env-gated, no auth. `getProfile()` takes no arguments. An interface that cannot
express "which profile" cannot grow an accidental multi-tenant code path. The
table enforces the same thing — `id` is a boolean primary key constrained to
`true`, so a second row is not representable.

**The driver is injected, not imported.** `SqlExecutor` is a one-method type
matching `client.query(text, params)`. node-postgres satisfies it directly;
postgres.js and Drizzle need a one-line wrapper. This keeps the dependency count
at zero, keeps the package publishable, and lets the tests run against a fake
executor with no database.

**Evidence is a measurement, not a sentence.** `voice-builder` insists that
off-limits and never-does entries come from observed absence across the samples
— "no em dashes (0 of 5 samples)". Stored as free text that is a claim; stored
as `{ observed: 0, total: 5 }` it is data that can be recomputed when the sample
set changes, filtered on, or checked for staleness. `formatEvidence()` is the
single place it becomes prose, and it renders the identical string. Validation
treats it like a measurement too: whole numbers, non-zero denominator,
`observed <= total`. `{ observed: 7, total: 5 }` is not a rounding error, and
letting it through would write "7 of 5 samples" into a file a skill reads as
fact.

**`schemaVersion` and `updatedAt` belong to the store.** Neither appears on
`VoiceProfileInput`, so a client cannot backdate a write or claim a schema
version it does not conform to. `schemaVersion` is stored per row so a future
migration can tell a v1 payload from a v2 one without inferring it from shape —
free to add now, impossible to add retroactively once there is data.
`updatedAt` is what the sync banner stamps, which is what makes staleness
detectable.

**Input is looser than storage.** A rule can be a bare string when nothing was
measured, and every field except the author's name can be omitted, so a
half-finished interview still saves as a draft. `parseVoiceProfileInput`
narrows the loose form and reports *every* problem it finds, not just the first.

**Rows are validated on read, not trusted.** Stored JSON may predate a schema
change or have been edited by hand in a SQL console.

**Headings are the real contract.** The strings in `render.ts` must match
`voice-builder`'s output exactly. A skill grepping for `## Signature phrases`
finds nothing if it is renamed. The test suite asserts every heading in both
files for this reason.

**`renderMarkdown` is pure; the banner lives in `sync`.** The projection has no
"generated file" preamble, so the same function can feed an LLM without shipping
it a do-not-edit notice. The banner belongs to the artifact, not the content.

## Layout

```
src/
  types.ts             types only — no logic, no I/O, no imports
  validate.ts          loose input → strict stored shape
  render.ts            VoiceProfile → markdown / system preamble (pure)
  sync.ts              store → disk. Server-only; the one node:fs import
  store.ts             the VoiceStore interface
  adapters/
    postgres.ts        plain SQL over an injected executor
    memory.ts          for tests, and proof the seam is real
test/
  voice-profile.test.ts
```

## Tests

```bash
npm test          # from the repo root
```

Node's built-in runner with native TypeScript stripping. No test framework, no
build step, no database.

**The Postgres adapter has never touched a real Postgres.** Its tests run
against a fake executor, which proves the SQL is parameterized and the shapes
round-trip — and proves nothing about whether the DDL applies, whether `jsonb`
round-trips as expected, or whether the upsert behaves under a real connection.
That is the first task of Step 3, tracked in `SETUP.md`.

## Extracting this package

1. `git mv packages/voice-profile ../voice-profile-core`
2. Drop the `voice-profile-core` path aliases from the root `tsconfig.json`.
   Imports read `from 'voice-profile-core'` already, so no source changes.
3. Add a build step (`tsc`) and point `main`/`types` at `dist/`. Relative
   imports use explicit `.ts` extensions, so enable
   `rewriteRelativeImportExtensions` or switch them to `.js`.

Nothing else. There are no host imports to unpick — that was the point.
